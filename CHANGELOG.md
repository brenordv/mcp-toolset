# Toolset Changelog
## v23
- Updated MCP: `git-ops` to v2.3.0. `git_grep` and `git_ls_files` gained `globs` (wildcard pathspecs with git's default matching, so `*.cs` matches at any depth and `crates/*/*/Cargo.toml` works) and `excludePaths` (git's `:(exclude)`; a directory drops its subtree, and on its own it searches everything else). Before this, the server ran git in literal-pathspec mode, so a wildcard in `paths` matched nothing and an `:(exclude)` entry was ignored, both with an empty or unfiltered success. That global mode is gone; every pathspec now carries a server-chosen prefix (`:(literal)` for `paths`). Behavior change: a `paths` entry with `*`, `?`, or a leading `:`, or an empty one, is now `RejectedArgument` on every tool that takes `paths`. On Linux and macOS, a tracked file whose name starts with `:` can no longer be blamed or addressed through `paths`, and one whose name contains `*` or `?` can no longer be addressed through `paths`. The `argv_built` log line drops `--literal-pathspecs` and masks the new pathspecs as `<glob>` and `<exclude>`.
- Updated MCP: `git-ops` to v2.4.0. `git_log` gained `perlRegex` (git's `--perl-regexp` for `grep` and `author`, so `A|B` alternation and `\d` work; the default stays git's basic regular expression, where `|` is a literal and an alternation returns no commits) and `allRefs` (git's `--all`: every ref under `refs/` plus `HEAD`). A git built without PCRE2 returns `PcreUnavailable` for `perlRegex: true`. `allRefs` together with `ref` is `RejectedArgument`. Behavior change: `git_log` now always passes `--basic-regexp` or `--perl-regexp`, so a `grep.patternType` in the user's or the repository's git config no longer changes how `grep` and `author` match. The `argv_built` log line for `git_log` shows the dialect flag, and `--all` when set.
- Updated MCP: `git-ops` to v2.5.0. `git_file_at_ref` gained `lineStart`/`lineEnd` (1-based, inclusive, both or neither, as in `git_blame`), `byteOffset`, and `maxBytes` (a UTF-8 byte cap that sets `truncated` and never splits a character at 4 bytes or more). The payload gained `total_lines` and `next_byte_offset`; pass `next_byte_offset` back as `byteOffset` to read the next page. Before this, a large or single-line file (one 50 KB line was enough) overflowed the MCP client's per-result limit and could not be read at a ref at all. There is no default cap, so a call without the new parameters returns the whole blob as before. No log change.
- Updated MCP: `git-ops` to v2.6.0. `git_grep` gained `countOnly` (git's `-c`): one `{path, match_count}` entry per file with matching lines instead of every line, where `match_count` counts lines, not occurrences. Before this, a broad pattern returned thousands of lines and overflowed the MCP client's per-result limit, and `maxCount` capped the matches instead of counting them. `maxCount` together with `countOnly` is `RejectedArgument`, since git applies `-m` before counting. A new Warning log event, `count_parse_empty`, fires when git reports a match but no count record parses. Fixed: `git_grep` returned an empty success when the user's or the repository's git config set `color.ui` or `color.grep` to `always`; it now always passes `--no-color`, which the `argv_built` log line shows.
- Updated MCP: `text-search` to v1.5.0. `search_text` gained `count_only`: one `{path, match_count}` entry per file with matching lines instead of every match, counted the same way as `git_grep` `countOnly` (lines, not occurrences) and never capped by `max_matches_per_file`. The envelope gained `total_match_count`, the sum over every page, present only in count mode. Before this, `files_only` gave no counts and a broad pattern's match list overflowed the MCP client's per-result limit. Count results page like `files_only`, and every page re-reads the selection. `count_only` together with `files_only` is `InvalidArgument`. No log change.
- Updated hook CLI: `skill-stats-cli` to v1.1.0. It now also runs on Claude Code's `UserPromptExpansion` event with `matcher` `.*`, next to the `PostToolUse` entry on the `Skill` tool: a skill or slash command you type expands into the prompt without a tool call, so the `PostToolUse` entry alone recorded only skills the model invoked. Add the new entry to `~/.claude/settings.json` per the CLI README and keep the old one. A `UserPromptExpansion` payload's skill name comes from `command_name` and its arguments from `command_args`; the `tool_input` fields are still read first, so a `PostToolUse` payload records as before, and the `prompt` field (the whole typed line) is never read. `command_args` is the argument text typed after the command name, stored as before. Behavior change: a recording failure exits 1, never 2, since exit 2 on `UserPromptExpansion` blocks the user's prompt; exit 1 lets it through with a non-blocking hook error notice, and the stderr line's prefix is now `skill-stats-cli:`. A payload with no recognized name field is skipped with the new reason `unrecognized_shape` (`no_skill` now means a name field that is empty or only slashes), and those two skip lines in `ingest-errors.log` carry `root_keys=[...]` (names only) after `tool_input_keys` when the root object has properties; the `oversize` skip carries neither. Each key list logs up to 32 names (was 16). The ingest writer gives up on a locked store after 1 s (SQLite busy timeout and Microsoft.Data.Sqlite command timeout, which were 5 s and 30 s), and the documented hook `timeout` is 10 s.
- Updated MCP: `skill-stats` to v1.1.2. The `StoreUnavailable` message for a missing store now names the `skill-stats-cli` hook instead of the `PostToolUse` event, and the README documents the two-event wiring (`UserPromptExpansion` plus `PostToolUse`), the upgrade from a `PostToolUse`-only setup, and a recording check. No log change.
- Updated MCP: `git-ops` to v2.7.0. Fixed: `git_diff`, `git_show`, and `git_stash_show` returned an empty file list, with no error, when the user's or the repository's git config set `color.ui` or `color.diff` to `always`, because git colored the patch and no `diff --git` header parsed; a repository could use this to hide its changes from `git_diff`. The three now always pass `--no-color`, as `git_grep` has since 2.6.0; `statOnly` was not affected. A new Warning log event, `patch_parse_empty`, fires when the `--numstat` pass of `git_diff` or `git_stash_show` lists files but no `diff --git` header parsed from the patch. The `argv_built` log line for the three tools shows `--no-color` on every pass.
- Updated MCP: `text-edit` to v1.6.0. `replace_text` now counts a regex that times out on a file in the session's `regex_timeouts_total`, once per file and dry runs included; before this the counter always read 0 and the timeout showed only as that file's `refusal_reason`. Log change: a new Warning line, `event=regex_timeout` with `refusal_reason=regex_timeout`, `tool=replace_text`, and the call's `call_id`, once per timed-out file; no new field. `regex_timeouts_total` in the `server_stop` `metrics_summary` now counts them. Corrected the `SkippedFile` doc comment, which omitted the `ignore_file` undo skip reason added in v21.
- Updated MCP: `text-search` to v1.6.0, `text-edit` to v1.7.0, and `skill-stats` to v1.2.0. Fixed: the `exception_tail` log field, written when startup fails or when the host or the MCP SDK logs an exception, carried the last 512 bytes of the exception's message and stack trace, which can name a file by its absolute path. It now carries the exception's type chain only, outer to inner (for example `System.IO.IOException -> System.Net.Sockets.SocketException`), at most eight entries and then ` -> ...`. Log change: the content of `exception_tail`; the field name is unchanged. The `server_start_failed` line no longer carries the startup reason, which stays on stderr (`<server>: fatal error: ...`).
- Updated MCP: `text-search` to v1.7.0 and `text-edit` to v1.8.0. Fixed: an extra deny entry containing a `/` (`MCP_TEXTSEARCH_EXTRA_DENY=**/.claude/settings*.json`) did not cover a text-search call whose `cwd` was at or inside the directory it names, because the denylist was tested against the path relative to the `cwd` only, so `find_files` listed the file and `read_lines` returned it. The path relative to the base root (or the package root) is now tested too, in the walk, in explicit `paths`, and in the read gate. text-edit builds its selection through the same code: with the same entry in `MCP_TEXTEDIT_EXTRA_DENY`, a scoped selection now drops such a file instead of reporting it refused as `denied`, so it no longer counts in the `batch` log line's `attempted` and `refused`. Unscoped calls are unchanged. No log shape change: a scoped text-search `read_lines` or `read_json` of such a file now emits the existing `refusal` line (`refusal_reason=denylisted`) and counts in `refusals_total.denylisted`.
- Updated runtime NuGet dependency: `Microsoft.Data.Sqlite` 10.0.11 → 10.0.13, used by `file-vault`, `text-edit`, `skill-stats`, and `skill-stats-cli`. 10.0.13 fixes a race in the library's connection pool: a connection being opened could be taken by a pool clear or a leak sweep on another thread, then disposed (its next use threw `ObjectDisposedException`) or lent to a second caller while the first still used it. In `file-vault` and `text-edit`, two tool calls running at once could share one connection, and one of them then failed with an internal error (`SqliteException`); the server log carries SQLite's `cannot start a transaction within a transaction`. A `text-edit` call that failed that way after writing its files left its journal rows pending, and undo restores pending rows without the hash check, so review such a batch before undoing it. No wire or log change.
- Updated MCP: `git-ops` to v2.8.0. Fixed: a repository's own config could make `git_log`, `git_show`, `git_reflog`, and `git_stash_list` run a program it names. With `log.showSignature=true`, git verifies each signed commit it shows by running the program `gpg.program`, `gpg.ssh.program`, or `gpg.x509.program` names, and a forged `gpgsig` header is enough. Every git call now passes `-c log.showSignature=false`, next to the `core.fsmonitor` and `core.hooksPath` neutralizers. With `log.showSignature=true` in the user's own config, `git_log` and the `git_show` metadata pass also put gpg's output in front of each signed commit's `hash`, and `git_log`, both `git_show` passes, and `git_reflog` ran gpg once per signed commit shown; the same change fixes both. Log change: every `argv_built` debug line shows `-c log.showSignature=false`, and its `argv_len` is 2 higher. The bootstrap `rev-parse` calls carry the same pin but log no argv line.
- Updated MCP: `git-ops` to v2.9.0. Fixed: in a repository whose config names a promisor remote (`remote.<name>.promisor=true`, `remote.<name>.partialCloneFilter`, or `extensions.partialClone`), a tool call that read an object git did not have made git fetch it from that remote, and the fetch ran the program the repository's config names for the transport, for example `remote.<name>.uploadpack` for a remote at a local path or `core.sshCommand` for ssh. Every git process the server starts now gets `GIT_NO_LAZY_FETCH=1`, next to `GIT_TERMINAL_PROMPT=0`. git 2.45.1 and later and the May 2024 security releases for 2.39 to 2.44 have the full check (the `git-ops` README's Requirements lists them); 2.45.0 honors the variable only in part, and an older git ignores it. Behavior change: in an ordinary partial clone, a call that needs an object the clone has not fetched (an old blob for `git_show`, `git_diff`, `git_blame`, `git_file_at_ref`, or `git_grep` with `ref`) fails with `GitCommandError` instead of fetching it.
- Updated MCP: `git-ops` to v2.10.0. Fixed: a filter driver that a repository's config names (`filter.<driver>.clean` or `filter.<driver>.process`), selected through a `filter` attribute in `.gitattributes` or `.git/info/attributes`, ran when `git_status`, a worktree `git_diff`, or `git_blame` without `ref` read a worktree file; for `git_status`, every file whose timestamp no longer matched the index, which is every file in a copied repository. Before each `git status`, `git diff`, and `git blame`, the server now lists the drivers the config names and pins each one's `clean`, `smudge`, and `process` to empty and `required` to `false` with `-c`. A driver name that contains `=` or is not valid UTF-8, or a listing longer than the 8 MB output cap, fails the call with `GitCommandError`. Fixed: `git_status` and a worktree `git_diff` made git run `git status` inside each checked-out submodule, with the submodule's own config and filter drivers; both now pass `--ignore-submodules=dirty`. Behavior change: drivers from your global config are pinned too, so a file under git-lfs, git-crypt, or another filter is compared as its raw worktree bytes: `git_status` can list it as modified when only its timestamp changed, a worktree `git_diff` shows the stored pointer or ciphertext against the raw content, and `git_blame` without `ref` attributes every line to the uncommitted working-tree version. In a repository you trust, running `git status` once in your own shell, with the filter installed, refreshes the index's timestamps and clears those files from `git_status` and a worktree `git_diff`. A submodule with only uncommitted changes inside it is no longer listed by `git_status` or a worktree `git_diff`; one whose commit moved still is, even where `submodule.<name>.ignore` or `diff.ignoreSubmodules` would hide it. Log change: each `git status`, `git diff`, and `git blame` process is preceded by a `git config` process with its own `argv_built` and `subprocess_exit` debug lines under the same `call_id`; that `subprocess_exit` shows `git_exit_code` 1 when the config names no filter driver, which is not an error. The pins show in the next `argv_built` line as `-c <filter_driver>`, four per driver, with `argv_len` 8 higher per driver, and the `argv_built` line for `git_status` and for each `git_diff` pass that reads the working tree shows `--ignore-submodules=dirty`. A listing that hits the output cap, or a driver name the server cannot pin, logs only the call's `tool_error` at Error, with the fixed message and no `git_exit_code`. `suspicious_filter_invocation` is unchanged, and with the pins in place no call should produce it. Metrics change: the listing is a git subprocess, so `subprocess_duration_ms_p50` and `subprocess_duration_ms_p95` get one more sample per `git_status` and `git_blame` call and two more per `git_diff` call, and are not comparable with an earlier version's `server_stop` summary. A listing that hits the 8 MB cap counts in `truncations_total`. The two refusals count as `error` in `tool_calls_total` and not in `git_command_errors_total`, which counts only git exits a tool does not allow.
- Updated MCP: `text-search` to v1.8.0 and `text-edit` to v1.9.0. Fixed: which ignore files a directory holds was decided by `File.Exists` per name, which reports an existing file as absent when the server cannot read its attributes or list its directory, so such a file's rules were silently not applied. Presence now comes from the directory listing, and ignore-file names match case-insensitively on every platform. Behavior change: a text-search `read_lines`, `read_json`, `inspect_files`, or `search_text` call that names a path inside a directory the server can enter but not list now fails with `InternalError`, as does a walk whose `cwd` is such a directory or lies under one; a walk still skips such a subdirectory, and a subdirectory the server can list but whose ignore file it cannot open now fails the walk. text-edit's `replace_text` and `normalize_files` fail the same way, before any write, for a `paths` entry inside such a directory or a sweep scoped beneath one; no batch is written. The `tool_error` log line for the failed call names the directory by its root-relative path (`.` for the root) and the filesystem exception type; no new log field. Both servers share the fix through `Common.Files`.
- Updated MCP: `git-ops` to v2.11.0. Fixed: `git_diff`, `git_show`, and `git_stash_show` reported a changed file under the whole `diff --git` header line instead of its path when the user's or the repository's git config set `diff.noprefix`, `diff.mnemonicPrefix` (worktree, staged, and `HEAD`-to-worktree diffs), `diff.srcPrefix`, or `diff.dstPrefix`, because the parser reads the path after ` b/`; the numstat overlay then missed the file. With `diff.submodule` set to `log` or `diff`, a changed submodule was missing from `files`. `git_diff` and `git_show` now pass `--src-prefix=a/ --dst-prefix=b/ --submodule=short` next to `--no-color` on every diff pass. `git_stash_show` passes `--submodule=short` and pins the prefixes with `-c diff.noprefix=false -c diff.mnemonicPrefix=false -c diff.srcPrefix=a/ -c diff.dstPrefix=b/`, because `git stash show` in git 2.52.0 through 2.55.x garbles a prefix given on its command line. Fixed: with `diff.submodule=diff` in a repository's config, a `git_diff`, `git_show`, or `git_stash_show` whose diff included a submodule commit change made git start `git diff` inside the submodule, without `--no-ext-diff` or `--no-textconv`, so an external diff command or textconv driver the submodule's own config names could run; `--submodule=short` overrides the key, and git starts no process inside the submodule. Log change: the `argv_built` debug line shows the three new flags on each `git diff` pass of `git_diff` and on the `git_show` patch pass, with `argv_len` 3 higher, and on each `git stash show` pass of `git_stash_show` the four `-c diff.*` pairs in front of the fixed `-c` pairs plus `--submodule=short`, with `argv_len` 9 higher.

## v22

Before this, a sweep over more files than `max_files` (default 1,000) acted on the first 1,000 and reported `truncated: false`, so an agent could believe it had covered every file. The `batch` log line carries `truncated`, and the session's `truncations_total` now counts these sweeps, dry runs included. Behavior change: a mutation envelope always carries `skipped_symlinks`.
- Updated MCP: `text-search` to v1.4.6 and `text-edit` to v1.5.0. When an ignore file (`.gitignore`, an agent-ignore file, or `.mcpignore`) existed but could not be read, for example because another process held it locked, the server log line for the failed call carried the file's absolute path. The line now names the ignore file by its path relative to the walked root. The call still fails with `InternalError`; an ignore file the server sees but cannot read is never treated as empty. Both servers share the fix through `Common.Files`.
- Documented that `text-edit` can write client and agent configuration files inside the base root (`.mcp.json`, `.claude/settings.json`, a user's `.claude.json`) on purpose, and how to make them unwritable: `MCP_TEXTEDIT_EXTRA_DENY=.mcp.json;.claude.json;**/.claude/settings*.json`. The `MCP_TEXTEDIT_EXTRA_DENY` and `MCP_TEXTSEARCH_EXTRA_DENY` descriptions now say what an entry containing `/` is matched against (the base root for `text-edit`, the call's scope for `text-search`). Corrected the `text-edit` README, which said a denylisted file named in `paths` is reported as refused (it is dropped from the selection without a report), and `text-edit` doc comments that described per-file refusals as counted in `refusals_total` (only a rejected `cwd` is). Removed the `undo_mismatch` log field, which nothing wrote, from the allowlist. No behavior change.

## v18

- Updated MCP: `text-search` to v1.4.2 and `text-edit` to v1.3.1. An ignore-file line (`.gitignore`, an agent-ignore file, or `.mcpignore`) that translated to an invalid .NET regex made every content tool fail with `InternalError` (`RegexParseException`), even a literal `search_text` or an `inspect_files` call, because the ignore files between the base root and a scoped `cwd` are read on every gated read. ## v17

## v16
- Updated MCP: `git-ops` to v2.1.0 and `file-vault` to v3.2.0. Both now return a structured error for an unbindable tool argument instead of the SDK's opaque `An error occurred invoking '<tool>'.`. A call whose argument names do not fit a tool's schema is rejected before the tool runs, naming unknown keys, suggesting the likely intended name, listing missing required names (such as a `git_status` with no `cwd`), and echoing `expected_arguments`; a known argument of the wrong JSON type (for example `vault_save` `tags` passed as a comma-joined string rather than an array) is reported with the same code after the SDK's binder rejects it, carrying the SDK's fixed generic text in `sdk_error`. This ports the mechanism `text-search` gained in v15 to the other two servers. Behavior change: an unknown argument name alongside valid ones is now rejected rather than silently ignored. Genuine `file-vault` domain errors (`conflict`, `not_found`, and the rest) keep their own code.
- Extended the same structured argument-shape error to `text-edit` (v1.3.0) and `skill-stats` (v1.1.0), and extracted the shared name-validator into a new `Common.Mcp` library that all five servers now reference, removing the per-server copies. `text-edit` carries the full `detail` (expected names, suggestions, `sdk_error`); `skill-stats`, whose error body is a code and a message only, carries the diagnostics in the message instead. `text-search` moved to `Common.Mcp` as an internal refactor (v1.4.1); no wire change.

## v15

Argument-shape mistakes now come back as the standard failure envelope with `error.code` `InvalidArgument` instead of a bare, bodiless SDK message: a call whose argument names do not fit a tool's schema is rejected before the tool runs, naming each unknown key, suggesting the schema name it likely meant when one is close (`isRegex` for `is_regex`, `globs` for `glob`), listing any missing required name, and echoing the full `expected_arguments`. ## v14
- Added a new `skill-usage` hook CLI (v1.0.0): a `PostToolUse` hook on the `Skill` tool that appends one row per skill invocation to a local SQLite store under `~/.skill-stats` (overridable via `SKILL_STATS_HOME`). Skill names are normalized by stripping leading slashes so `csharp` and `/csharp` are one skill. ## v9
- Made `.gitignore`/`.mcpignore` an un-overridable boundary in `text-search` and `text-edit`: an ignored file is never returned or edited, enforced at the read gate, the `paths[]` gate, listing, and the write gate. `include_ignored` now re-includes only the built-in default tier (`node_modules`, `bin`, `obj`, ...) and can never re-include a `.gitignore`/`.mcpignore` path, and a scoped `cwd` call now also honors ignore rules in directories above the `cwd`.
- Added content-based secret detection to `text-search`: a file whose content matches a known secret shape (private keys; AWS/Azure/GCP/Google keys; Slack/GitHub/Stripe/SendGrid tokens; URL-userinfo credentials) is withheld from `read_lines`, `search_text`, and `inspect_files` regardless of its name, while it still appears in `find_files` listings. On by default; `MCP_TEXTSEARCH_SECRET_SCAN=off` disables it and `=aggressive` adds higher-false-positive detectors (JWTs, generic password assignments). Disclosed in `describe_scope`.
- Closed a secret-exposure gap in `text-search` and `text-edit`: `local.settings.json` (the Azure Functions local config, which by convention holds connection strings and access keys) is now on the non-overridable secret denylist. `include_ignored` can no longer surface the file or leak its content through a search context window.
- Fixed the server log files, which were written as UTF-8 with a byte order mark. The rolling file sink now writes BOM-less UTF-8. This affects newly created and rolled log files; existing logs keep their BOM.
- Added per-platform publish convenience wrappers under `eng/`: `publish-windows`, `publish-linux`, `publish-macos` (osx-arm64), and `publish-macos-x64` (osx-x64), each in both `.ps1` and `.sh`. They delegate to `eng/publish.ps1` / `eng/publish.sh` with a fixed RID.
